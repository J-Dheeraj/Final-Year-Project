\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}

An artificial intelligence system's ability to exploit software does not establish that it can reliably secure it. This project extended an existing exploit-confirmation prototype into a two-part, evidence-gated system for using large language models to secure open-source software: (1) dynamic confirmation and patch validation for already-published CVEs, and (2) reachability-filtered static analysis on real upstream free5GC source. Across five evolving pipeline rounds and a 36-run hosted-Claude comparison, dynamic exploit confirmation proved consistently achievable: all six catalogue classes were confirmed at least once, and every hosted model confirmed all six exploits. Patch validation proved substantially harder, and its own acceptance criterion needed correction twice. The original two-check criterion was found, by trace-level inspection, to accept a patch whose vulnerable route had merely crashed, indistinguishable to the check from a genuine fix; this was corrected into a four-outcome verdict. External review then found that corrected verdict itself still only checked for crash-absence on a benign request, not correct legitimate behaviour: a limitation this project reproduced and closed where possible.

Three independent real-upstream cases reached this project's strongest standards of evidence: a real, pinned-version PyPI package (\texttt{jaraco.context}, CVE-2026-23949); a real, disclosed, unauthenticated-disclosure advisory in OpenEMR (GHSA-q366-cv5v-83w8), confirmed by content-verified request/response evidence and extending this method to a second domain, healthcare; and all four manually selected handlers of a real, disclosed free5GC vulnerability pattern, disclosed as four separate CVEs sharing one root cause (CVE-2026-40245 through CVE-2026-40248): a harness running the real vulnerable and patched \texttt{free5gc/udr} binaries in a fuller deployment (real MongoDB, real free5GC NRF) confirmed by direct HTTP exchange that the vulnerable build permits an unauthorized read of one record or the entire subscription collection, an unauthorized write, and an unauthorized delete, all through the same one-line missing-\texttt{return} defect, and that the real fix commit closes all four while preserving legitimate behaviour for the specific operations tested (a content-verified legitimate read, seed writes, and a separately confirmed legitimate delete). This project's contribution is not a single confirmation or patch-acceptance rate, but an account of how far an evidence-gated workflow can progress toward reproducible evidence, and where its own validation judgments can fail: a limitation found, fixed, and narrowed under independent review.

\chapter{Introduction}

\section{Background}

An artificial intelligence (AI) system's ability to exploit software does not establish that it can reliably secure it. In July 2026, OpenAI models undergoing cybersecurity evaluation with reduced safeguards bypassed isolation controls and compromised parts of Hugging Face's infrastructure \cite{openai-incident}. The incident reminded us why advances in automated exploitation must be followed up with careful evaluation of their defensive use.

Agentic AI offers one approach to automated security testing. An agent uses a Large Language Model (LLM), which processes text and code in order to select tools as well as revise its actions using feedback \cite{anthropic-agents}. For example, it would generate a test for a suspected vulnerability, run it, and investigate an unsuccessful attempt. Weiss and Khayet developed a pipeline that generates exploits from published vulnerability information and checks them against both vulnerable and patched software versions \cite{weiss-khayet}. Their method formed the basis of AI-exploit-CVE, a prototype developed and presented at DEFCON Singapore. Weiss and Khayet's account is a personal blog post used here as the origin of the idea being extended, not as evidence for any claim; the experimental records in this thesis were generated by this project; claims of dynamic confirmation are supported by the execution evidence described for each experiment. The system built in this project is an LLM-assisted workflow with code-defined stages and bounded feedback; autonomous tool selection is available on a separate optional path but is not the configuration evaluated in the model comparisons in Chapter~4.

Broader capabilities have emerged from the Defense Advanced Research Projects Agency's AI Cyber Challenge (AIxCC), which discovered 54 of 63 synthetic vulnerabilities and patched 43, approximately 86\% and 68\% of the total \cite{aixcc}. Its winning system, ATLANTIS, combines language models with program analysis to discover vulnerabilities and generate fixes \cite{atlantis}. The Open Source Cyber Reasoning System framework (OSS-CRS) provides a common interface for building and running automated vulnerability discovery and fixing systems \cite{osscrs}. These developments provide a foundation for extending the prototype beyond individual, disclosed vulnerabilities.

\section{Research Gap}

However, applying these capabilities requires evidence that the tests represent the software being assessed. An exploit that succeeds against a simplified reproduction may not work against the real application. Likewise, a patch that compiles may leave the vulnerability unresolved or disrupt legitimate functions. The central question for this project is therefore: what executable evidence is sufficient to distinguish exploit confirmation, patch-screening success, and bounded functional preservation in an LLM-assisted known-CVE workflow, and where does each evidence tier fall short?

\section{Objectives}

This study aims to develop and evaluate an agentic workflow for confirming disclosed vulnerabilities and validating candidate patches with executable evidence, using the stage vocabulary and evidence-gating philosophy of ATLANTIS and OSS-CRS as a conceptual frame rather than integrating their implementations directly (Chapter~2 states precisely where this project's stages align with theirs and where they do not). The workflow is evaluated on two tracks: a catalogue of six disclosed CVEs reproduced as minimal local targets, and free5GC, an open-source implementation of a 5G wireless network core used for research and testing \cite{free5gc}, where a shared missing-\texttt{return} defect across four selected handlers of one source file is analysed and patched against the real, cloned upstream source rather than a reproduction, and evaluated as a real upstream runtime case. This single root cause is disclosed as four separate CVEs (CVE-2026-40245 through CVE-2026-40248), one per handler, all closed by the same upstream fix commit; Section~\ref{sec:free5gc-runtime-harness} states the exact handler-to-CVE mapping. Alongside compile-time verification of the broader four-handler patch set, the DELETE handler (CVE-2026-40246) was additionally run and exercised live, against a real local MongoDB instance, to confirm the exploit and the fix by direct HTTP exchange rather than by compilation alone. A further, narrower integration links the pipeline to ProvTrail, a companion student's tool for identifying JavaScript and TypeScript code resembling known vulnerable implementations; this integration is limited to SARIF-based ingestion plumbing and one hand-authored, dynamically confirmed demonstration case, not a systematic evaluation of ProvTrail's own flagged findings. SARIF, the Static Analysis Results Interchange Format \cite{sarif}, is the interchange format between ProvTrail's static findings and this project's dynamic-confirmation pipeline.

\section{Scope}

Evaluation covers the six-CVE reproduction catalogue described above, run across multiple verification rounds and across a comparison of eight locally hosted models plus a later 36-run comparison of six hosted Claude models, and the one free5GC case study, in controlled local environments; within that case study, all four analysed handlers (CVE-2026-40245 through CVE-2026-40248, Section~\ref{sec:free5gc-runtime-harness}) were additionally evaluated at runtime against a fuller deployment (a real, locally hosted MongoDB backend and a real free5GC NRF), rather than by compile-time verification alone, with OAuth2 enforcement explicitly disabled for these runtime checks (a later, separate follow-up, Section~\ref{sec:final-evidence-freeze}, extends a subset of them with OAuth2 enforcement turned on). This assesses whether suspected vulnerabilities can be dynamically reproduced and whether a proposed patch causes the original exploit to fail under an automated criterion. Full functional preservation (whether a patch also preserves the affected route's behaviour for a legitimate, non-malicious request, rather than merely the absence of a crash) was not part of the original broad synthetic evaluation across the full catalogue and every model compared. It was added later, at different evidence strengths, not as a check performed uniformly across every result in this evaluation: the real-upstream cases (Sections~\ref{sec:real-upstream-validation}, \ref{sec:openemr-validation}, and~\ref{sec:free5gc-runtime-harness}) use case-specific response-content or state checks against actual software, detailed per case in those sections, not a uniform full-response-equality protocol; for six synthetic patched artifacts available at reassessment time (Section~\ref{sec:corrected-validator}), the malicious side was checked only for the absence of the exploit's response marker, while the legitimate side was checked against real expected content of varying granularity per class. These are bounded observations for the tested inputs, not a guarantee of general patch correctness. Results obtained from simplified reproduction are distinguished from those obtained using actual software, with unsuccessful and inconclusive tests recorded. The findings are intended to help developers judge the evidence supporting an automated vulnerability report or proposed patch, including where that evidence, or the criterion used to produce it, was found to be incomplete.

\section{Project Phases and Scope Evolution}

The project proceeded in four broad phases over the academic year: extending the inherited exploit-confirmation prototype with dynamic execution and self-improvement; building and correcting the patch-acceptance criterion described in Chapter~4; porting and applying the reachability-filtering capability to real free5GC source and extending it to runtime confirmation; and the later multi-model comparisons, real-upstream validation cases, and final evidence freeze. This is a chronological grouping of when work happened over the academic year, not the same four-way split as the Methodology Overview's ``four main stages'' (Section~\ref{sec:methodology-overview}), which groups the same underlying work by pipeline component instead. The two do not, and are not intended to, map onto each other one-to-one. The work completed matches this final scope. The project was originally framed around fuzzing-based LLM security; when it became clear during implementation that no pipeline stage performs coverage-guided fuzzing, the framing was changed, with the supervisor's agreement, to LLM-assisted exploit confirmation and patch validation for already-disclosed CVEs — a change to stated framing only, with no technical restructuring and no planned work dropped.

Evaluation subsequently broadened to three further model-access methods beyond the Ollama and Claude CLI comparisons above (a direct Claude API gateway with 10 requested model names, the OpenAI API with 23 model identifiers, and the Codex CLI with 18 model identifiers, together 51 requested model/access combinations across the same free5GC, OpenEMR, and six-CVE-catalogue targets, not 51 distinct models that were each successfully evaluated: some names overlap across methods, many produced no output at all, and only 4 of the 10 gateway names resolved) summarised in Section~\ref{sec:extended-access-comparison} and reported in full in the project repository's \texttt{docs/RESULTS\_BY\_ACCESS\_METHOD.md} and \texttt{docs/FINAL\_EVIDENCE\_SUMMARY.md}, rather than reproduced chapter-by-chapter here alongside the original Ollama/Claude CLI comparisons they extend.

\section{Ethics and Responsible Use}
\label{sec:ethics}

All exploitation and patch testing in this project was carried out against locally hosted, self-controlled targets: either generated reproductions run on a private development machine, or a real upstream package (\texttt{jaraco.context}) and two real upstream repositories (\texttt{free5gc/udr} and OpenEMR) exercised entirely within isolated local environments the author controlled, never against a public or third-party service. No exploit generated by this project was deployed against, or tested on, any system outside the author's own local infrastructure, and no live production service, public deployment, or third party's data was accessed, probed, or affected at any stage. Every CVE and advisory studied is real and already publicly disclosed (verified against NVD, GHSA, and the relevant upstream project's own advisory or fix commit before use, per Appendix~\ref{app:reproducibility}); CWEs are the weakness classification each advisory carries, not a separate class of disclosed advisory. This project did not discover, disclose, or otherwise handle any previously unknown vulnerability, so no responsible-disclosure obligation to a vendor arose during this work. Local HTTP servers used to serve crafted archives or payloads (for example, the real-upstream \texttt{jaraco.context} case, Section~\ref{sec:real-upstream-validation}) were bound to \texttt{127.0.0.1} only and never exposed beyond the local machine. Should this project's methodology be extended to a previously undisclosed finding in future work, the author commits to following standard coordinated/responsible disclosure practice (privately notifying the affected project or vendor, allowing a reasonable remediation window, and withholding public detail until a fix is available) rather than the immediate, open reporting appropriate for the already-published CVEs studied here.

\chapter{Literature Review}
\label{chap:literature-review}

\section{Overview}

This project sits at the intersection of three bodies of work: agentic AI systems that use large language models (LLMs) to carry out multi-step security tasks, Cyber Reasoning Systems (CRSs) that automate vulnerability discovery and repair at scale, and reachability-based static analysis techniques that narrow the scope of what such systems must examine. This chapter reviews each area in turn. It moves from isolated per-system description toward the connecting themes, ending with the specific gap — evidence-gated confirmation of both exploits and patches against representative targets — that motivates this project's objectives, introduced in Chapter~1.

\section{Agentic AI for Automated Security Testing}

An agent, in the sense used throughout this literature, is a system in which an LLM processes text and code, selects among available tools, and revises its own actions based on feedback from their results, rather than following a fixed script \cite{anthropic-agents}. This feedback loop is what distinguishes an agentic approach from a single-shot LLM query: an agent that generates a candidate exploit can, in principle, run it, observe whether it succeeded, and try again with the failure in hand.

Fang et al.\ reported that GPT-4 exploited 13 of 15 one-day vulnerabilities within up to five attempts, while performance fell to 1 of 15 without the vulnerability descriptions. Other evaluated models and scanners recorded no successes under their respective test conditions. This demonstrates strong dependence on the supplied advisory information in that benchmark \cite{fangkang}. A follow-up evaluated a hierarchical agent team on 14 post-cutoff vulnerabilities without supplying their descriptions, reporting a 4.3$\times$ pass@1 improvement over GPT-4 without descriptions \cite{fangkangzeroday}. Weiss and Khayet demonstrated this same loop concretely for vulnerability exploitation, showing that an agent could take a published CVE's advisory text and generate a working exploit against it in under fifteen minutes \cite{weiss-khayet}. Their pipeline formed the direct basis for AI-exploit-CVE, the prototype this project extends. CVE-GENIE reproduced 428 of 841 selected CVEs and reported an average cost of \$2.77 per CVE \cite{cvegenie}. These larger-scale results provide context, while differences in case selection, validation and cost accounting prevent a direct performance or efficiency comparison with this project's fully described six-CVE catalogue with selective trace-level audits (Chapter~4).

Both what Weiss and Khayet established and what they left open matter for how this project is scoped: they showed that advisory-to-exploit generation is tractable for an agent, but their evaluation, like much of the broader "AI can hack" literature this project's Introduction opens with \cite{openai-incident}, centres on the offensive capability itself rather than on how confidently a defender could trust the result. An exploit that an agent reports as successful and an exploit that has actually been shown to work against a representative target are not the same claim, and the literature reviewed here does not consistently distinguish between them.

PoC-Gym quantifies exactly this gap for Java CVEs: of 116 LLM-generated candidates that passed its own runtime validation (completed execution and produced a success signal), only 65 also passed post-hoc verification against the actual vulnerable code location: meaning 51 of 116 runtime-valid candidates failed its annotated-location verification \cite{pocgym}. This project's own dynamic-confirmation stage (Section~\ref{sec:implementation-procedure}) is designed against exactly this risk, replacing an earlier design where generated exploits were written to disk but never actually run with one that checks the exploit script's real process exit code; PoC-Gym's result is a reminder that this choice narrows the gap rather than closes it outright.

\section{Cyber Reasoning Systems and the AIxCC/OSS-CRS Ecosystem}

A Cyber Reasoning System generalises the single-exploit agentic loop into a full pipeline: discover an unknown vulnerability in a codebase, triage it, generate a proof of vulnerability, and generate and validate a patch, all without a human specifying the bug in advance. DARPA's AI Cyber Challenge (AIxCC) evaluated seven finalist CRSs (Atlantis, Buttercup, RoboDuck, FuzzingBrain, Bug Buster, Artiphishell, and Lacrosse) against a shared benchmark of synthetic vulnerabilities seeded into real open-source projects, with the finalists collectively discovering 54 of 63 seeded bugs (86\%) and patching 43 (68\%), per DARPA's own results announcement and, independently, a subsequent systematic peer-reviewed analysis of the competition's design, architectures, and results \cite{aixcc,sokaixcc}. The winning system, ATLANTIS, combined LLM-driven reasoning with traditional program-analysis techniques across its discovery, triage, and patch-generation stages \cite{atlantis}, and the Open Source Cyber Reasoning System project (OSS-CRS) subsequently generalised several AIxCC-era systems into a common runtime so they could be pointed at real OSS-Fuzz projects rather than only the competition's own challenge problems \cite{osscrs}.

Two things follow from reading AIxCC and OSS-CRS alongside Weiss and Khayet's narrower exploit-generation work, stated as an observation and a hypothesis rather than an established finding. AIxCC's aggregate 86\%-discovery/68\%-patch split, reported across seven finalist systems on a large competition benchmark, is not directly comparable in task, scale, or denominator to this project's own six-CVE confirmation/patch-validation results (Section~\ref{sec:aixcc-comparison}), and this project's own patch-validation numbers have themselves been shown, by trace-level inspection, to include at least one false acceptance (Chapter~4): so neither figure should be read as an independently reliable measurement to compare against the other. What both bodies of work do suggest, more cautiously, is that generating a working patch may plausibly be harder than discovering or confirming the underlying bug across genuinely different systems and scales; this project's own results are consistent with that hypothesis without independently proving it holds as a general property of the task. Second, AIxCC and OSS-CRS finalists are primarily full discovery systems (they find vulnerabilities nobody has previously identified) though this is not absolute: FuzzingBrain, one AIxCC finalist, includes a documented mode for assessing externally supplied findings (for example, from static-analysis tools) rather than only its own discoveries \cite{fuzzingbrain}, which is closer in spirit to a known-finding confirmation task than a pure discovery system. This project's own scope remains narrower still and more specific: it confirms and patches already-published CVE advisories specifically, with dynamic execution evidence for every case, rather than triaging static findings of unstated provenance. This project's scope is distinguished not by an assertion that known-CVE execution confirmation is absent from the field -- CVE-GENIE, for instance, explicitly performs it -- but by its particular combination: a small, fully described catalogue, documented harness defects, and an investigation of what each evidence tier can and cannot establish.

\section{Reachability-Filtered Vulnerability Triage}

A separate line of work addresses a different bottleneck: even once a codebase is the analysis target, an LLM or static analyser cannot practically reason over every function in a large real-world project. OpenAnt addresses this by decomposing a codebase into a call graph and performing breadth-first reachability analysis from attacker-controlled entry points, reporting scope reductions of up to 97\% on real projects including OpenSSL, WordPress, and Flowise, before applying LLM-driven adversarial verification and sandboxed dynamic testing to the reduced candidate set \cite{openant}. An independently reported AIxCC finalist system, FuzzingBrain \cite{fuzzingbrain} (competition repository name \texttt{afc-crs-all-you-need-is-a-fuzzing-brain}), converges on a similar three-stage shape (static reachability partitioning, LLM-based "suspicious point" triage, then fuzzing-driven verification) arrived at separately from OpenAnt's own design.

OpenAnt's and FuzzingBrain's independent convergence on the same three-stage shape is at least suggestive that reachability-first filtering is not an idiosyncratic design choice specific to one system, though this observation rests on the small, non-systematic set of sources reviewed for this chapter rather than a comprehensive survey of the field, and should be read with that scope in mind.

Patch validation rigour in this literature varies: FuzzingBrain's own published validation criteria require a patch to compile successfully and to pass a supplied regression-test suite before being accepted \cite{fuzzingbrain}, which is at least as strong as, and in the regression-testing respect stronger than, this project's own two-check acceptance criterion (Section~\ref{sec:patch-generation-validation}). A stated criterion is not the same as a reliably enforced one, however, and FuzzingBrain's own paper reports this directly: a missing-parameter bug silently caused its Python validation subprocesses to fail during the competition itself, so that, in the authors' own words, ``many patches were submitted without verification against known POVs'' \cite{fuzzingbrain}, discovered only in post-competition analysis. This gap between a patch passing validation and a patch actually being correct is not new to LLM-based repair, and is not unique to this project's own validator failure described in Section~\ref{sec:patch-generation-validation} either: Qi, Long, Achour, and Rinard's decade-old analysis of three classical generate-and-validate repair systems (GenProg, RSRepair, and AE) found that errors in the validation infrastructure itself meant most reported patches were not even plausible under their own test suites, and that approximately 90\% of patches judged plausible were equivalent to deleting the relevant functionality rather than fixing it: establishing that passing a validation suite and being a correct patch have never been the same claim, well before LLMs entered the picture \cite{qiplausibility}.

Two recent studies examine validation using different designs: VulnRepairEval reports low repair performance under exploit-based differential validation -- requiring the original PoC to fail against the patched code, not merely that the patch applies -- with even the best of twelve evaluated LLMs repairing only 5 of 23 real-world Python CVEs under that criterion in that baseline evaluation \cite{vulnrepaireval}. PVBench separately quantifies overestimation by a weaker validation procedure: 42.3\% of patch attempts that passed its basic checks (1{,}250 of 2{,}952) failed its stronger, developer-authored ``PoC+'' tests, which encode root-cause and specification intent beyond mere exploit-blocking \cite{pvbench}. This project's own round-5 false-acceptance finding (Section~\ref{sec:patch-validation-lag}) (a patch accepted by a basic two-check criterion that trace-level inspection later showed was an unrelated crash, not a deliberate fix) is a single, concrete instance of the general validation problem these studies discuss; it does not replicate PVBench's paired comparison or VulnRepairEval's benchmark evaluation.

What distinguishes this project's own reachability work (Chapter~3) is not a general gap in the literature's rigour, but a specific combination: applying reachability-filtered triage to an already-disclosed CVE and verifying the resulting patch by cloning the actual upstream repository and rebuilding it against that project's real, unmodified dependency graph. This project explicitly records that checkout, patch application, and rebuild step; the OpenAnt paper describes sandboxed exploit tests but does not report this particular rebuild-and-patch-compilation procedure, which supports a statement about what its publication documents, not proof its system never performs the step. This project's free5GC case study demonstrates the combination for one real vulnerability, detailed further in Chapter~3; it is offered as this project's own bounded implementation and validator-failure analysis, not as evidence that the wider literature lacks compile-time verification or known-CVE execution confirmation altogether (CVE-GENIE, for instance, explicitly performs known-CVE reproduction and verification \cite{cvegenie}).

\section{Research Gap}

Three observations from the small set of sources reviewed above motivate this project's objectives; they are offered as a rationale drawn from a limited, non-systematic review, not as a claim about the full field. First, agentic exploit generation (Weiss and Khayet, and the broader capability the Hugging Face incident illustrates \cite{openai-incident}) has been demonstrated as tractable, but the evaluations reviewed here do not consistently separate "the agent reports success" from "the exploit was dynamically confirmed against a representative target": a distinction this project treats as a first-class requirement rather than an afterthought. Second, AIxCC-class systems are primarily oriented toward discovering previously unknown vulnerabilities at competition scale (with FuzzingBrain's external-finding assessment mode a partial exception); this project instead studies a narrower, everyday situation (triaging a dependency's already-disclosed CVE) with a lighter-weight, dynamic-evidence workflow scoped specifically to that task, without claiming from the small set of sources reviewed here that this situation is underserved by the field as a whole. Third, reachability-filtered triage (OpenAnt, FuzzingBrain) is established as an effective scope-reduction technique, with FuzzingBrain's case specifying stringent compile-and-regression-test validation criteria whose enforcement was itself undermined by a documented infrastructure bug, as discussed above; what remains specific to this project is combining that filtering technique with compile verification against a real, live-cloned upstream project's dependency graph for an already-disclosed CVE, rather than a claim that the wider literature omits compile-time verification.

This project studies the following combination under its own stated conditions, distinct from each source reviewed above in a specific, statable way. Building on Weiss and Khayet's own execution-based workflow (their published method already executes generated exploits against vulnerable and patched versions in a sandboxed evaluation loop, not merely generates and describes them statically \cite{weiss-khayet}), this project added dynamic execution to the inherited local prototype it actually extends, AI-exploit-CVE, which had not yet implemented that step; introduced a two-check patch-acceptance criterion and documented its own validator failures in detail; and evaluated selected real-upstream cases (Chapter~3). Unlike the evaluation described in OpenAnt's own 2026 arXiv paper \cite{openant}, it verifies a reachability-filtered patch by cloning and rebuilding the actual upstream repository and checking it compiles against that repository's genuine dependency graph (Chapter~3). That comparison is against that specific, dated publication, not against OpenAnt the open-source project's current state, which has continued to develop since that paper. OpenAnt's repository, as of this writing, documents a separate ``Auto Patcher'' feature that likewise clones a real repository checkout and applies a candidate patch to a temporary copy of it, so ``sandbox'' is not treated here as the categorical opposite of ``real upstream repository'' for that current tool. Unlike the AIxCC-aggregate figures, this project reports its own exploit-confirmation and patch-acceptance rates across multiple models and multiple verification rounds on a small, fully described catalogue (Chapter~4), so its own discovery/patch pattern can be inspected directly rather than assumed to match AIxCC's aggregate. Findings for JavaScript and TypeScript, via the ProvTrail integration introduced in Chapter~1 (SARIF-based, \cite{sarif}), extend this same evidence-gated approach to a second ecosystem.

\chapter{Methodology}

\section{Project Context}

This project extends an existing single-vulnerability exploit-confirmation prototype, AI-exploit-CVE, into a two-part evidence-gated system for using large language models (LLMs) to secure open-source software: (1) LLM-assisted exploit confirmation and patch validation for already-published CVEs, and (2) reachability-filtered static analysis on real upstream source, applied to a disclosed vulnerability in free5GC, an open-source 5G core network implementation \cite{free5gc}. ATLANTIS and OSS-CRS (Chapter~2) inform this project's stage vocabulary and evidence-gating philosophy rather than being integrated as code: no component of ATLANTIS or OSS-CRS is imported, called, or run by this project, and Appendix~\ref{app:crs-mapping} states explicitly where the analogy between this project's stages and theirs holds and where it does not. A secondary integration links the pipeline to ProvTrail, a companion project that statically identifies JavaScript/TypeScript code resembling known-vulnerable implementations; this integration currently consists of SARIF ingestion plumbing (\texttt{provtrail\_bridge.py}) and one hand-authored, dynamically confirmed JavaScript case (CVE-2024-48910, Prototype Pollution), not a systematic evaluation of ProvTrail's own flagged findings against real scanned projects, and this narrower scope is stated here rather than implied by the architecture description alone. The system falls under the Software System/Application category, with a Data Analytics component in its reachability-filtering and metrics stages.

\section{Methodology Overview}
\label{sec:methodology-overview}

This project was carried out in four main stages. First, the existing CVE-driven exploit-confirmation pipeline (advisory intake, vulnerability classification, exploit-artifact generation, dynamic execution, self-improvement on failure, and patch generation with regression validation) was extended and hardened against a catalogue of six published CVEs spanning six vulnerability classes. Next, a reachability-filtering engine (ported from an earlier, standalone prototype developed for the same project before its scope was redirected) was applied to a real, disclosed CVE in free5GC, producing an AST-based call graph reduction and a patch verified to compile against the actual upstream dependency graph. ProvTrail's SARIF/AI-text export was then integrated as an additional advisory source, so the pipeline could be driven by statically located JavaScript/TypeScript findings rather than only by NVD/GHSA feed entries. Finally, the system was evaluated across multiple rounds of live, locally hosted LLM verification (using Ollama-served open-weight models \cite{ollama}), during which two implementation defects were identified, fixed, and re-verified, and the pipeline's evidentiary claims were confirmed to hold under live model generation as well, not only under stubbed responses.

\subsection*{High-level workflow}
\begin{enumerate}
 \item Advisory intake: fetch a CVE/GHSA advisory, or consume a ProvTrail-flagged finding, as the unit of work.
 \item Vulnerability classification: categorise the advisory into one of six classes (SSRF, SQL injection, OS command injection, XSS, path traversal, deserialisation), or, for a memory-safety-class advisory, dispatch to the main pipeline's own dedicated probe (\texttt{\_probe\_memory\_safety}), which generates and compiles a minimal C proof-of-vulnerability harness directly; this is a separate mechanism from, and does not call into, the reachability engine described in step~7 below, which operates independently on real upstream Go/C/C++ source rather than on advisory text.
 \item Exploit-artifact generation: synthesise a proof-of-concept and a minimal reproduction target from the advisory's described bug pattern.
 \item Dynamic execution: run the generated artifact against the reproduction target and record a real process exit code / HTTP response as evidence.
 \item Self-improvement: on a genuine, executed failure, attempt a fix via a persisted lesson, then an LLM-generated revision, then a rule-based fallback, bounded to three iterations.
 \item Patch generation and validation: generate a candidate patch and accept it only if the original exploit now fails against it and the target's health check still passes. This is the original acceptance criterion as first implemented; Chapter~4 reports a discovered flaw in it and the stronger, four-outcome \texttt{patch\_verdict} criterion this project uses as its headline patch metric from that chapter onward.
 \item Reachability analysis (parallel track): parse real upstream source into an AST-derived call graph, perform breadth-first reachability from stated entry points, and generate and compile-verify a patch against the real dependency graph.
 \item Reporting and metrics: aggregate per-CVE outcomes into structured reports and summary metrics (confirmation rate, patch-acceptance rate, reachability reduction, wall-clock time, LLM call count).
\end{enumerate}

\section{Alternative Approach Considered}

Before continuing with the existing advisory-driven architecture, a proposed redesign was evaluated and deliberately not adopted: replacing CVE-driven exploit confirmation with a pipeline in which an LLM reads raw source code with no prior knowledge of any specific advisory, hypothesises a vulnerability from scratch, synthesises a triggering input purely by reasoning rather than by search or mutation, and validates the hypothesis by replaying that input once against an instrumented build. This alternative was rejected for four reasons. First, its own proposed validation plan (a single smoke test against one example file) was judged insufficient grounds to commit to restructuring the project's architecture before that assumption was independently tested. Second, this project's existing exploit-artifact generation is always guided by an advisory's own stated root cause, a materially easier task than zero-shot vulnerability hypothesis generation with no prior knowledge, so this project's own results do not transfer as evidence that the alternative's harder, blind variant would work. Third, the proposal would have introduced a second, disconnected system rather than extending the existing, already-validated pipeline. Fourth, it required setting up new local model infrastructure for a speculative direction while the existing, evidence-gated pipeline was already in a documented, working state. This alternative remains available to revisit as a bounded, separately-evaluated extension, but was not adopted as the basis for this project.

\section{System Architecture}

\subsection{System Description}

The system consists of two loosely coupled subsystems sharing a common advisory-driven design philosophy. The first, the main exploit-confirmation pipeline, is orchestrated by \texttt{cve\_pipeline.py} and driven by a feed poller (\texttt{cve\_watcher.py}) that dispatches pipeline runs for newly observed advisories from NVD, GHSA, or ProvTrail. The second, the reachability-filtering engine (\texttt{src/reachability/}), operates independently on real upstream source rather than on advisory text, and is invoked directly against a stated set of entry-point functions. A supporting bridge module (\texttt{provtrail\_bridge.py}) converts ProvTrail's SARIF output into advisories the main pipeline can consume, and two standalone dynamic-exploitation labs (\texttt{ssrf\_lab/}, \texttt{free5gc\_lab/}) provide locally hosted, self-controlled targets for live confirmation where a generic Flask stand-in would not suffice.

\subsection{Implementation Procedure}
\label{sec:implementation-procedure}

The system was implemented incrementally, in the following order. First, the pre-existing exploit-confirmation pipeline was extended with dynamic execution, replacing an earlier design in which generated exploit artifacts were written to disk but never actually run. Self-improvement was then added as a bounded retry loop that checks, in order, a persisted-lesson store, an LLM-generated revision, and a rule-based fallback. Patch generation and validation was implemented next, gated on two simultaneous conditions: the original exploit failing against the patched target, and the target's health check continuing to pass. The reachability engine was subsequently ported from an earlier standalone prototype and re-validated against its own prior results before being applied to real free5GC source, first as an isolated file parse and later against the actual cloned upstream repository to confirm compile-compatibility with its full dependency graph. The ProvTrail bridge and the free5GC dynamic-exploitation lab were implemented as independent, loosely coupled additions, following the same dual vulnerable/patched-mode convention already established elsewhere in the system. Finally, the system was run across successive live-model verification rounds; two defects that surfaced during this process (Section~\ref{sec:confirmation-rate-progression}) were each isolated with a targeted test, fixed, and verified via a full-catalogue re-run.

\section{Testing and Validation}
\label{sec:testing-validation}

\subsection{Testing Strategy}

The system was tested by executing every generated exploit artifact as a real subprocess against a real, locally deployed target and recording its actual exit code or HTTP response, rather than treating generation as evidence of exploitability by itself. Patch validation was tested by re-running the original, unmodified exploit against the patched target and independently confirming a separate \texttt{/health} endpoint still responded correctly, so that a patch which crashed the target process entirely would be rejected. This check does not confirm that the vulnerable route itself still behaves correctly for a legitimate request, only that the application as a whole is still running; Chapter~4 reports a case where this specific gap allowed a patch containing an unrelated crash bug to be marked validated. For the reachability track, the generated patch was tested for compile-compatibility by cloning the actual upstream repository at the pre-fix commit, applying the patch to the real source file, and rebuilding against the module's genuine dependency graph. The DELETE handler (CVE-2026-40246) was first tested at runtime using a minimal local harness. A fuller Docker deployment with a real NRF subsequently extended runtime testing to all four selected handlers (CVE-2026-40245 through CVE-2026-40248, Section~\ref{sec:free5gc-runtime-harness}).

Three of the four handlers (DELETE, single-record GET, PUT) are disclosed under CWE-285 (improper authorisation check); the fourth, collection GET, is disclosed as CWE-200/202/209 (information exposure). Section~\ref{sec:reachability-filtering} reports how this project's own rule-based classifier's output compares against these four disclosed labels. The DELETE handler (CVE-2026-40246) is additionally the real-upstream counterpart to this project's separate, hand-written \texttt{free5gc\_lab/} reproduction of the same CVE: the same CVE validated two ways, at two evidence tiers, not two different CVEs.

The real, cloned \texttt{free5gc/udr} module was built twice from source, once at the vulnerable commit and once at its immediate successor, the real upstream fix commit. Both builds require a reachable MongoDB instance to start; a native MongoDB Community Server instance, run locally rather than inside a container, was used, since the experiment's only real infrastructure dependency was UDR's own database connection, not full containerisation. Both builds also require a reachable Network Repository Function (NRF) to complete their own startup: UDR's registration call to the NRF blocks its HTTP server from starting at all if it never succeeds, an infinite retry with no timeout, so a minimal stand-in NRF, answering only the one registration call UDR needs and asserting no broader NF-discovery capability, was required purely to let each build reach the point of serving real HTTP traffic. This stand-in had itself to be implemented as a small compiled Go program communicating over cleartext HTTP/2 (h2c), rather than a simpler HTTP/1.1 script, because free5GC's own NRF client negotiates HTTP/2 unconditionally and rejects an HTTP/1.1 responder outright. With both dependencies satisfied, each build was driven through an identical request sequence over real HTTP: seed a subscription record, issue the CVE's malicious delete request, check whether the record still exists, reseed, issue a legitimate delete request for the same record, and check again: with every request, response, and process log captured as part of the resulting evidence bundle rather than only the final pass/fail outcome.

This minimal harness was subsequently extended to a fuller deployment and to the three remaining reachable handlers, using the official \texttt{free5gc-compose} Docker stack rather than the hand-written stand-in above: a real, official MongoDB image and a real, official free5GC NRF image (not a minimal stub), with a custom-built UDR image compiled from the same pinned vulnerable and fixed commits. OAuth2 enforcement, which the real NRF enables by default and which would otherwise require a full OAuth2 client-credentials flow unrelated to the vulnerability under test, was explicitly disabled in the NRF's configuration for this harness; this is a real, supported free5GC configuration option, not a synthetic bypass, but it means this result alone says nothing about whether OAuth2 enforcement would affect an attacker's ability to reach these handlers in a deployment that has it enabled (a later, separate follow-up, Section~\ref{sec:final-evidence-freeze}, closes part of this gap for two of the four handlers' read operations specifically). Under this fuller deployment, all four of the reachability engine's originally-flagged handlers (not only the DELETE handler) were driven through a malicious request and a seeding/setup write, with every request, response, and container log captured; a single explicit benign-request check (a legitimate single-record read with the correct \texttt{influenceId}) was run once per build and used as this harness's overall benign-path signal, not repeated as a separate, independently content-checked legitimate request for every handler.

This project does not use a training/testing split or k-fold cross-validation; it is not a statistical learning system. Instead, validation ran across five successive live-model rounds of the full CVE catalogue, with each round's failures traced to a specific, named cause before the next round was attempted, rather than accepted as unexplained noise.

These metrics were selected to mirror the vocabulary used by DARPA's AI Cyber Challenge and the OpenSSF's OSS-CRS project to report cyber-reasoning-system results (bugs confirmed against bugs attempted, proof-of-vulnerability confirmation rate, and patch-acceptance rate) so that this project's results can be read against the same benchmark context introduced in Chapter~1, rather than against an ad hoc scale.

To keep these terms precise across the results reported in Chapter~4, evidence tiers are distinguished explicitly rather than collapsed into a single pass/fail label.

\begin{description}
\item[Dynamically confirmed] means a recorded subprocess execution outcome, HTTP exchange, or compiled-harness run, each real and not a static description.

\item[Patch accepted by the two-check criterion] means the original, unmodified proof-of-concept no longer meets its success condition against the patched local target, while a separate \texttt{/health} request still succeeds. This checks exactly one attack input and application liveness; it does not establish that the affected route handles a legitimate request correctly, that other attack inputs are blocked, or that the named upstream package has been repaired. This project does not use the term ``plausible patch'' or claim ``regression-safety'' for this flag: Chapter~4 reports a specific case (CVE-2026-78683, round 5) where the tested exploit request crashed the patched route with an unrelated import error, and this satisfied the exact criterion above, which is why a stronger label would overstate what it proves. This criterion is also weaker than the patch-validation bar used by at least one real AIxCC finalist system, FuzzingBrain, whose own published criteria require a patch to compile, eliminate all known proofs of the vulnerability, and pass a supplied regression-test suite \cite{fuzzingbrain}. This project's own two-check criterion does not match that three-part bar, though FuzzingBrain's own stricter bar was itself silently undermined by a validation-infrastructure bug during the competition (Chapter~\ref{chap:literature-review} discusses this further), a failure mode of the same general kind this project independently found and corrected in its own pipeline.

\item[A further tier, ``correct'' patch] (one independently checked against the real upstream fix's own intent, or against benign-request and multi-payload behaviour, rather than only against the one exploit that triggered it) is, at this stage of the pipeline, not yet measured by this project across the main catalogue; no second-reader adjudication against the real upstream fix's own intent is performed anywhere in this project, and this project's own patch-validation investigation (Section~\ref{sec:patch-generation-validation}) shows why that distinction matters in practice. The benign-request half of this gap is later closed, for a bounded set of cases, not left purely as a limitation: Section~\ref{sec:corrected-validator}'s content-verified reassessment checks benign-path behaviour against real expected content of varying granularity per class (full JSON equality, a specific field value, or a substring check) for six patched artifacts available at reassessment time, and the three real-upstream cases (Sections~\ref{sec:real-upstream-validation}, \ref{sec:openemr-validation}, and~\ref{sec:free5gc-runtime-harness}) use case-specific response-content or state checks against actual software, detailed per case in those sections rather than a uniform full-response-equality protocol. These remain bounded observations for the tested inputs, not a guarantee of general patch correctness, and second-reader adjudication specifically remains unmeasured throughout the whole project.

\item[Diff-similarity scoring] is also not purely absent: a separate, later free5GC-specific study (\texttt{docs/PATCH\_QUALITY\_SCORING\_RESULTS.md}) line-diffed 14 already-generated free5GC patches for one target function against the real upstream fix's own version of that function, finding 9 of 14 byte-identical and the remaining 5 (all smaller Ollama models) differing by 1--3 lines. Of those 5, 4 passed every recorded runtime check (\texttt{confirmed\_fix\_all\_four\_handlers}); the fifth, \texttt{qwen2.5-coder:1.5b} (95.52\% textually similar to the real fix, differing by only 1--2 lines), did not: its own runtime sweep records \texttt{collection\_get\_leak\_fixed: false} and \texttt{overall\_verdict: partial\_or\_inconclusive}, the same partially-correct patch already discussed in Section~\ref{sec:free5gc-llm-patch-sweep} (it appends an unrelated response line rather than the needed \texttt{return}). This is a useful illustration in its own right: high textual similarity to the real fix does not by itself establish that the patch is functionally correct. This is a textual-similarity proxy on one narrow, single-statement fix, not a semantic-correctness guarantee or a second-reader adjudication, and does not extend to the main catalogue's patches.

\item[Compile-verified] describes the free5GC reachability case study's original compile-only evidence and means \texttt{go build} succeeds against the real, live-cloned upstream module with the patch applied: explicitly weaker evidence than dynamic confirmation, and never reported in the same column without this qualification.

\item[Runtime-confirmed] All four of that case study's reachable handlers (CVE-2026-40245 through CVE-2026-40248, Table~\ref{tab:free5gc-handler-cve-map}) were subsequently runtime-confirmed: the real, cloned module was built, run, and exercised over real HTTP for both the vulnerable and fixed commits, first against a minimal MongoDB-only stand-in (Section~\ref{sec:free5gc-runtime-harness}) for the DELETE handler, then against a fuller deployment (real MongoDB and a real free5GC NRF, OAuth2 disabled) for all four handlers, meeting the same dynamically confirmed bar defined above rather than the weaker compile-verified one.
\end{description}

\section{Limitations and Assumptions (Method-Related)}
\label{sec:limitations-method-related}

The methodology rests on several stated assumptions and bounds, listed here individually rather than run together, so each can be checked on its own terms.

\begin{enumerate}
\item \textbf{Reproduction versus the real package.} The methodology assumes that a faithful reproduction of an advisory's described bug pattern is representative evidence of that bug class, even where the reproduction target is a minimal stand-in rather than the actual named upstream package. For the six main-catalogue CVEs, the exploited target is a generated Flask application reproducing the described pattern; a confirmed exploit therefore demonstrates that the described pattern is exploitable as written, not that the real, named package is exploitable when actually installed and run. The SSRF probe performs live HTTP and callback checks against a controlled lab reproduction, not the real, named \texttt{lmdeploy} package.

\item \textbf{Static pattern matching versus dynamic evidence.} Four of the remaining five classes (SQL injection, OS command injection, XSS, deserialisation) rely on static pattern matching at the probe stage, with dynamic evidence instead attributed to the execution step. The fifth, path traversal, is a partial exception at this specific stage: its probe (\texttt{\_probe\_path\_traversal}) also runs a generic, target-independent runtime demonstration that a \texttt{"../"}-style path genuinely escapes a sandboxed base directory under Python's own path-join semantics, which is a real executed check, not a regex match; it does not execute the named package's own vulnerable function, so it remains distinct from, and weaker than, the execution-step evidence described next.

\item \textbf{What the two-check patch-acceptance criterion does and does not show.} A patch accepted by this project's two-check criterion has only been shown to make one known exploit request fail while a separate health endpoint still succeeds; this is not general correctness, not freedom from all other exploitable inputs, and (established by direct trace inspection in Chapter~4) not even reliably regression-safe, since the criterion cannot distinguish a deliberate security fix from an unrelated crash bug in the generated patch, both of which produce the same observable pattern (the exploit request fails, the separate \texttt{/health} endpoint still returns 200). Neither check currently confirms that the patched route itself still behaves correctly for a legitimate, non-malicious request (only that the application process as a whole remains alive), which is a concrete direction for strengthening the validation criterion, not merely a hypothetical one, since Chapter~4 reports a case where this exact gap produced a false acceptance. A corrected validator, introduced later in Chapter~4 (Section~\ref{sec:corrected-validator}), strengthens the exploit side of exactly this gap by distinguishing a deliberate rejection from a crash; its own benign-route check, however, was itself found to require only crash-absence rather than correct behaviour, so this limitation is narrowed, not resolved, and the same caution applies to reading its own results.

\item \textbf{The free5GC reachability case study's compile-to-runtime progression.} The free5GC reachability case study's four handlers were originally verified only to compile against the real upstream dependency graph, which is a real but bounded result: it does not by itself constitute dynamic confirmation, and one handler is additionally known to be only partially correct under the project's own rule-based patcher (Chapter~4), fully preserving compilation but not fully closing its handler's vulnerability under that generated patch (the real upstream fix used for runtime testing does not share this limitation). All four handlers were subsequently taken further, by a narrower route than a full core-network deployment: neither the minimal MongoDB-only harness nor its fuller successor stands up free5GC's other network functions (AMF, SMF, and the rest), and the fuller deployment's real NRF was run with OAuth2 enforcement disabled, so this remains real dynamic confirmation for this one file's four handlers under that specific configuration, not evidence that free5GC's broader core-network behaviour would confirm the same way under this stronger standard. A later, separate follow-up (Section~\ref{sec:final-evidence-freeze}) closes part of the OAuth2 gap specifically, for two of the four handlers' read operations, finding enforcement does not change their exploitability by a credentialed caller; this does not extend to the write and delete handlers or to the broader core-network question.

\item \textbf{Stubbed versus live-model verification.} LLM-dependent pipeline stages were first verified using stubbed model responses to establish that the surrounding logic functioned correctly, and were subsequently confirmed to operate under live model generation for exploit-artifact generation, self-improvement, and patch generation alike: every patch attempt in the eight-model local catalogue comparison (Section~\ref{sec:multi-model-comparison}) used real, metered Ollama calls, not a stub; the later 36-run hosted-Claude comparison (Section~\ref{sec:claude-multi-model-comparison}) and the further OpenAI/Codex/AIxTech sweeps (Section~\ref{sec:extended-access-comparison}) likewise used real, metered calls to their respective backends, not Ollama.

\item \textbf{The free5GC LLM-generated patch sweep's own under-fit cases.} The reachability engine's own separate LLM-based patch fallback was initially verified only via stub, since the free5GC case study's original patches were produced by its rule-based path instead; this was subsequently closed (Section~\ref{sec:free5gc-llm-patch-sweep}) by asking real local and hosted models to generate the fix for the one handler the rule-based patcher under-fixes, from scratch, with 6 of 8 local models (7 compiled) and 7 of 8 hosted Claude models passing the existing four-handler runtime harness. Two of those 8 local-model outputs illustrate different limitations, one of them not among the 6 passes: \texttt{qwen2.5-coder:1.5b}'s patch compiled but did not pass the runtime harness at all, recorded as \texttt{partial\_or\_inconclusive}; \texttt{codellama:13b}'s patch did pass the harness and is 98.51\% textually similar to the real fix, but closer static inspection shows it still omits the required \texttt{return} on the malformed-\texttt{snssai} branch, a branch the harness's own request set never exercises (Section~\ref{sec:free5gc-llm-patch-sweep}). A harness pass should accordingly be read as passing the specific branches this harness exercises, not as an exhaustive repair guarantee for the handler.
\end{enumerate}

\subsection{Patch Generation and Validation}
\label{sec:patch-generation-validation}

Across rounds 1--3 of the main pipeline's live-LLM catalogue runs, zero of the attempted patches were accepted by both conditions of the two-check criterion (the original exploit failing against the patched target, and the target's health check continuing to pass). Round 4 and round 5 each produced one patch accepted by this criterion, both for CVE-2026-78683 (Insecure Deserialization) and both resulting in the patched target returning HTTP 500 when the original exploit was re-run, satisfying the pipeline's first condition.

Trace-level inspection of both patches found the two HTTP 500 responses have different, and differently trustworthy, causes. Round 4's patched handler deliberately raises \texttt{ValueError("Deserialization only allowed for safe classes")} from an added class whitelist, consistent with the patch summary's own description and plausibly a genuine security fix, though this project's evidence for it stops at that trace-level reading. Round 5's patched handler, by contrast, raises \texttt{NameError: name 'io' is not defined}: the generated patch called \texttt{io.BytesIO(...)} without importing the \texttt{io} module, a plain implementation bug, not a security check of any kind (both traces reproduced in full in Appendix~\ref{app:trace-excerpts}). Because the pipeline's two-check criterion treats \emph{any} exception on the vulnerable route, deliberate or accidental, identically to a successful block, it could not distinguish these two cases: round 5's \texttt{patch\_validated: true} flag is a \textbf{false acceptance} by trace-level inspection, not a verified repair.

Round 5's patch was genuinely re-probed with its two recorded alternate payloads, each returning ``still blocked''; this does not establish the vulnerability was closed. The preserved trace shows the \texttt{NameError} occurs in a line constructing the unpickler before any payload-specific branching is reached, consistent with the crash being independent of payload content — a logical inference from the traceback's location, not confirmed by a preserved benign-request trace or the patched source itself (not preserved outside its temporary sandbox path, Appendix~\ref{app:repo-access}). The two probes therefore ran, but at minimum re-confirm the same crash rather than demonstrating the vulnerability was closed.

\subsubsection*{A corrected validator}
\label{sec:corrected-validator}

The false-acceptance finding above was addressed directly, not merely documented. The two-check criterion was extended, additively, with two new checks and a headline verdict field on the same underlying report object: \texttt{patch\_exploit\_blocked} (the exploit fails without an unhandled exception in the target's own process log, via a crash-signature pattern), \texttt{patch\_function\_preserved} (a fixed, non-malicious benign request to the same route completes without that same crash-signature pattern; precisely what this field does and does not establish is stated below, since it is weaker than it may first appear), and a headline \texttt{patch\_verdict} taking one of four outcomes: \texttt{confirmed\_fix} (blocked and preserved), \texttt{regression\_broke\_route} (blocked but the benign request also now fails), \texttt{inconclusive\_crash} (the exploit request itself crashed the route), and \texttt{not\_blocked} (the exploit still succeeds). The pipeline's current source has since relabelled \texttt{confirmed\_fix} as \texttt{heuristic\_fix\_screened} in new reports; the original \texttt{patch\_validated} flag is unchanged. Replaying the round 5 false-acceptance trace (Appendix~\ref{app:trace-excerpts}) through the corrected validator reproduces \texttt{patch\_validated: true} as before, while the new \texttt{patch\_verdict} field correctly reads \texttt{inconclusive\_crash}: the corrected criterion catches, automatically, exactly the case that previously required manual trace inspection.

\textbf{What \texttt{patch\_function\_preserved} does and does not establish.} The benign probe reuses the same generated proof-of-concept script with a fixed, generic non-malicious payload substituted for the exploit's own payload, rather than a class-specific request with a known-correct expected response. \texttt{patch\_function\_preserved} is set to true when that probe's target process executes and the same crash-signature pattern used for \texttt{patch\_exploit\_blocked} does not appear in its log: it does \emph{not} require the benign request to return HTTP 200, does not require the reused proof-of-concept script to itself report success, and does not check any class-specific expected output. A direct audit of every \texttt{confirmed\_fix} verdict in the 36-run hosted-Claude comparison (Section~\ref{sec:claude-multi-model-comparison}), prompted by external review, found that all 27 such verdicts' benign probes were reported as failed by the reused proof-of-concept script's own logic (a generic payload does not trigger that script's exploit-specific success marker), and that only 13 of those 27 returned HTTP 200 on the benign request's final response, with the remaining 14 returning 401, 403, or 400: a clean HTTP-level rejection, not a crash, but also not confirmation that the route handled the legitimate request as intended. Every reading of \texttt{patch\_verdict} = \texttt{confirmed\_fix} in this project from Section~\ref{sec:claude-multi-model-comparison} onward should accordingly be understood as ``the exploit was rejected without a detected crash, and a generic benign request to the same route also completed without a detected crash,'' not as independent confirmation that the route's legitimate behaviour is correct.

\textbf{A stronger, content-verified reassessment.} This limitation was addressed directly: for each of the six main-catalogue vulnerability classes, a real expected malicious result (its response status, recorded for context) and a real expected legitimate result (a class-specific expected-content assertion), both read from the actual generated target/proof-of-concept source, were defined and re-tested against surviving patched artifacts from the 36-run comparison; the malicious side's own check asserts only marker absence, not the recorded status. Locating those artifacts surfaced a further harness gap: only 6 of the original 36 patched targets were available on disk at the time of the reassessment, one per CVE, since Stage 3.5/3.8's artifact writer saves generated files to a shared, non-model-specific path every model touching the same CVE overwrote. Re-testing those 6 available artifacts under the stronger criterion, every one passed: each malicious request's class-specific check found no response marker (recorded statuses 401, 400, 400, 400, 403, and 200), and each legitimate request's response matched real expected content, ranging per class from full JSON-object equality to a specific field value or an HTML substring check, a materially stronger check than the malicious side's marker-absence test even though it is not uniformly exact full-response equality across all six classes. This reassessment also resolved an apparent contradiction: \texttt{claude-opus-4-8}'s surviving CVE-2026-46492 patch, originally recorded \texttt{not\_blocked}, passed this reassessment because the original multi-payload bypass check's alternate payload triggered the generated target's own vulnerability-signalling self-check without the markup ever being capable of executing in a real browser — a fidelity limitation of the target's signal, not a real bypass. Full methodology and per-CVE values: \texttt{reports/\allowbreak patch\_reassessment\_2026-09-26/\allowbreak RESULTS.md}. This reassessment does not extend to the other 30 of 36 original attempts, whose patched source no longer exists, and the 6 survivors are not a representative sample of the full comparison.

Under the corrected validator, this round's four confirmed exploits each received a patch attempt, and every one failed to close the vulnerability (three \texttt{not\_blocked}, one \texttt{inconclusive\_crash}): the same qualitative pattern as round 5, now distinguished explicitly, and zero \texttt{confirmed\_fix} results.

A separate, dedicated investigation tested whether a patch accepted by the two-check criterion could still be bypassed by a different payload, surfacing and fixing four further implementation defects (an unstripped markdown fence, a patch missing Flask's required \texttt{app.run()} block, a diagnostic log discarding the patched process's real standard error, and a \texttt{localhost} hostname resolving to two different locally bound services) distinct from the exploit-generation defects in Section~\ref{sec:exploit-confirmation-catalogue}. After fixing all four, a full eight-model, six-CVE re-test found 11/48 exploits confirmed, 9/48 patches attempted, and 3/48 accepted, a substantial rise from the 0/48 accepted in the original, pre-fix comparison (Section~\ref{sec:multi-model-comparison}).

This 3/48 figure requires one further qualification: all three nominally accepted patches had an empty \texttt{payload\_variants} field, meaning the multi-payload bypass check had no alternate payload to probe them with, because the small model that produced them (\texttt{qwen2.5-coder:1.5b}) did not successfully generate the alternate-payload section. A controlled synthetic test independently confirmed the bypass check itself works correctly: a deliberately narrow patch that blocklisted only the literal default payload passed the single-payload check but was correctly rejected once a structurally different payload was tried. The headline for this retest is therefore not ``3/48 patches validated,'' but \textbf{0/48 patches in this retest have been validated against more than their own original payload}: the bypass-testing mechanism is proven correct, but no patch here was exercised against it with a real alternate payload. This is narrower than a claim about the whole project: the main catalogue's own round-5 patch genuinely was re-probed with two alternate payloads, though that probe turned out to be uninformative for a different reason (Section~\ref{sec:patch-generation-validation}).

\subsection{Real-Upstream Validation: CVE-2026-23949}
\label{sec:real-upstream-validation}

Every result reported so far in this chapter, aside from the free5GC case study, exploits a generated Flask reproduction of an advisory's described bug pattern, not the actual named upstream package (Section~\ref{sec:limitations-method-related}). One case was carried out instead against the real, pinned-version package, to close part of that gap directly. CVE-2026-23949 (\texttt{jaraco.context}, a path-traversal defect in its \texttt{tarball()} helper) was selected as a tractable candidate: the advisory names a specific vulnerable range and fixed version, and the vulnerable function's real behaviour could be exercised without any special deployment beyond a Python virtual environment.

Two isolated virtual environments were built, installing the real, unmodified \texttt{jaraco.context==5.3.0} (the advisory's stated vulnerable range) and \texttt{==6.1.0} (its stated fixed version) from PyPI. The installed source in both was read directly to confirm the mechanism: \texttt{5.3.0}'s \texttt{strip\_first\_component} filter splits a tar member's path on its first \texttt{/} and keeps everything after it, including any \texttt{../} sequences, while \texttt{6.1.0}'s filter composes the same function with Python's standard-library \texttt{tarfile.data\_filter} (PEP 706), so \texttt{strip\_first\_component} runs first and \texttt{data\_filter} catches any surviving \texttt{../} sequence on the already-stripped member before extraction. A real malicious tar archive (a legitimate entry alongside one crafted to escape the extraction directory by two levels) and a real, non-malicious archive were served from a local, self-controlled HTTP server; the real, unmodified \texttt{jaraco.context.tarball()} function was called directly from each environment's own interpreter, with no mocking of the library under test.

Table~\ref{tab:real-upstream} reports the full four-way result. Read against the vocabulary in Section~\ref{sec:corrected-validator}: \texttt{patch\_exploit\_blocked} is true on \texttt{6.1.0} because the block is a named, documented standard-library exception (\texttt{tarfile.OutsideDestinationError}), not an unrelated crash signature; \texttt{patch\_function\_preserved} is true because the extracted file content was independently read back and confirmed to match on both versions, a stronger, content-verified check than the generic crash-absence probe used elsewhere (Section~\ref{sec:corrected-validator}) — practical here because a tar-extraction function's legitimate-use behaviour has one clear, checkable expected output, unlike every class in the main catalogue. \subsection{Real-Upstream Validation: OpenEMR (GHSA-q366-cv5v-83w8)}
\label{sec:openemr-validation}

\subsection{Reachability Filtering on Real Upstream Source}
\label{sec:reachability-filtering}

Applied to a real, 86~KB free5GC/UDR source file, the reachability engine parsed 102 functions and identified 4 as reachable from four HTTP entry-point handlers manually selected for this case study, not the module's complete externally callable surface: the same file defines dozens of other HTTP handlers (for AMF context, authentication status, PFD management, and more) that were not supplied as seeds. The resulting 96.1\% reduction is therefore a scope-reduction figure conditional on this seed selection and this one file's own call graph, not a completeness guarantee or a measured wall-clock speedup.

The call graph itself is name-keyed rather than symbol-qualified (two same-named functions or methods on different types are not distinguished, a documented limitation of the parser, \texttt{src/reachability/reachability.py}), and its traversal only follows calls visible as direct AST call sites within this one file; neither interface-dispatched calls resolved only at runtime nor calls into other files or packages are part of this specific reduction figure, so the 96.1\% bound applies to this file's own internal call graph, not to free5GC's full, cross-package call surface.

All four reachable functions were flagged by the rule-based pattern matcher and classified as CWE-285 (improper authorisation check), checked against each handler's own disclosed advisory (Table~\ref{tab:free5gc-handler-cve-map}), not confirmed by an independent second reviewer. Three of the four (DELETE, single-record GET, PUT) are disclosed under CWE-285 exactly; the fourth, collection GET, is disclosed as CWE-200/202/209 (information exposure), so this project's CWE-285 label for it is a broad authorisation-related interpretation, not exact agreement with its actual disclosed CWE.

A patch was generated for all four; applying all four to a live clone of \texttt{free5gc/udr} at the pre-fix commit, \texttt{go build ./...} completed successfully both before and after. One of the four generated patches is only partially correct: its target handler (\texttt{HandleApplicationDataInfluenceDataSubsToNotifyGet}) requires two separate \texttt{return} insertions in the real, disclosed fix, while the rule-based patcher inserts only the first match per function body, so that handler's vulnerability is not fully closed even though the module still compiles. This limitation is specific to this project's own rule-based auto-patcher, not to the real upstream fix used for the runtime testing described next, which takes all four handlers beyond this compile-time verification. This failure mode (addressing the fix site first noticed while leaving a structurally identical second site unaddressed) is not an idiosyncrasy of this project's patcher: a large-scale study of incomplete security fixes in the Linux kernel identifies ``overlooked similar modules'' as one of three recurring root causes of incomplete patches, alongside a developer misled by a crash's superficial symptoms rather than its underlying cause, in its root-cause analysis of a sample of such fixes \cite{incompletefixeskernel}. This one-vs-two insertion difference is a useful bounded comparison between this project's rule-based and model-assisted patchers for this specific defect, but it is not an ablation establishing that an LLM is necessary: a deterministic rule iterating over all matching sites in the function body, rather than stopping at the first match, could potentially close the same narrow defect without any LLM involvement.

The DELETE handler, sharing the same missing-\texttt{return} root cause and upstream fix commit as the other three, is disclosed as its own CVE, CVE-2026-40246 (Table~\ref{tab:free5gc-handler-cve-map}; Appendix~\ref{app:reproducibility} relates this result to the separately-evaluated, hand-written CVE-2026-40246 reproduction in \texttt{free5gc\_lab/}), and was subsequently taken one evidence tier further using the harness in Section~\ref{sec:free5gc-runtime-harness}: the real, cloned upstream module was built and run twice (vulnerable and fixed commits) against a real local MongoDB instance, driven with real HTTP requests rather than compiled but never executed.

At the vulnerable commit, the malicious delete request (invalid \texttt{influenceId}) received a \texttt{404} response, matching the handler's own validation check, but a follow-up read confirmed the targeted record had been deleted regardless: the vulnerable code writes the \texttt{404} response but does not \texttt{return} afterward, so execution falls through and performs the deletion anyway. At the real fix commit, the identical request again received \texttt{404}, but the follow-up read confirmed the record was still present: the added \texttt{return} stops execution before the deletion path. A legitimate delete request, with the correct \texttt{influenceId}, succeeded and removed the record on both builds, confirming the fix does not break the handler's intended function.

This gives a real, non-inconclusive verdict (\texttt{confirmed\_fix}) for this one handler, upgrading the free5GC case from compile-time to runtime evidence and giving it, at the time, the project's strongest patch-validation evidence among its compiled, real-upstream reachability work. The full evidence bundle (process logs, HTTP request/response logs, both commits' build logs, \texttt{manifest.json}/\texttt{verdict.json}, and the real upstream diff) is in Appendix~\ref{app:reproducibility}. At the time, this remained a single-handler result, not evidence the other three reachable handlers would behave identically; that gap was subsequently closed, as described next.

All three remaining handlers (collection GET, disclosed as CVE-2026-40245; single-record GET, CVE-2026-40247; PUT, CVE-2026-40248; Table~\ref{tab:free5gc-handler-cve-map}) were then run against the fuller Docker-based deployment described in Section~\ref{sec:free5gc-runtime-harness} (real MongoDB, real free5GC NRF, OAuth2 disabled), and were found to share the DELETE handler's exact root cause (the same missing \texttt{return} after a non-2xx write), with two of the three found to be more severe than the DELETE case on direct empirical inspection of the raw HTTP response bytes:

\begin{enumerate}
\item \textbf{Single-record GET.} Queried with an invalid \texttt{influenceId}, this handler returns \texttt{404 Not Found} with the literal body \texttt{"404 page not found"} on the patched build, but on the vulnerable build that same text is immediately followed, in the same response, by the real subscription's JSON content, with one \texttt{Content-Length} header sized to both writes combined (confirmed directly against the captured raw response in \texttt{evidence/RAW\_FINDINGS.md}, not inferred). The mechanism is the missing \texttt{return} in the Gin route wrapper: the invalid-\texttt{influenceId} branch writes the 404 but does not return, so execution falls through to the processor's own lookup by the separate \texttt{subscriptionId} segment, disclosing the real, previously seeded subscription — the invalid-\texttt{influenceId} check and the subscription's existence are unrelated checks, and failing the first does not stop the second. The captured response contains both writes in a single body. Writing an error response did not terminate the handler, so later code appended the subscription data.

\item \textbf{Collection GET.} Queried with no filter parameters at all (its own documented error condition), this handler shows the same pattern at larger scale: the vulnerable build's \texttt{400 Bad Request} error body is followed by a JSON array of \emph{every} subscription record in the system, since an empty filter matches every stored record: a full, unauthenticated collection dump inside what looks like a rejected request.

\item \textbf{PUT.} This handler goes further still: the request again returns \texttt{404 Not Found}, but a follow-up read confirms the submitted data was genuinely written to the MongoDB-backed subscription store: an unauthorized \emph{write}, not only a read leak.
\end{enumerate}

All three close cleanly on the patched build (the response body contains only the expected error text, and the follow-up read for \texttt{PUT} confirms nothing was stored). A legitimate, correct-\texttt{influenceId} request was separately verified unaffected on both builds for the single-record \texttt{GET} handler, the one case where this deployment's evidence bundle records a benign-path check; the collection \texttt{GET} and \texttt{PUT} handlers' legitimate-use behaviour was not separately re-tested here (DELETE's own legitimate path was verified in the earlier minimal harness). Combined with the DELETE result above, this constitutes a full CRUD bypass (unauthorized read of one record, unauthorized read of the entire collection, unauthorized write, and unauthorized delete) through one shared, one-line root cause, confirmed and closed across all four manually selected handlers. This work is recorded at commit \texttt{b8a4fe1}, kept isolated from the single-handler result's own evidence bundle; both are cited in Appendix~\ref{app:reproducibility}.

Zero of the 33, including all 18 raw-positive proposals, produced a dialog or uncaught-error signal within the observation window. The raw marker result remains preserved for audit.

Two interpretation rules apply to the numbers in this subsection. First, the free5GC headline result is a full pipeline validation outcome, not an independently model-generated one: four manually selected handlers are tested, but one handler change is model-generated and three are deterministic reachability materialisations, so the OpenAI sweep's 18/23 figure is not an 18/23 rate of independently model-generated patches. Second, the investigated failures in these later sweeps were attributed to a specific model's generation quality or a specific environment constraint after the harness corrections already described in this chapter, not asserted to exhaustively rule out every other cause; no access method's weaker results should be read as that access method being unsound on the evidence available.

\subsection{OAuth2-Enforced Follow-Up and Repeatability Check}
\label{sec:final-evidence-freeze}

Every free5GC runtime result reported above runs with OAuth2 enforcement explicitly disabled on the NRF. A follow-up closed this specific limitation for two of the four handlers: an opt-in compose override enabled OAuth2 without altering the default stack, and re-ran the collection-wide-read and single-record-read checks (plus the benign path) against both the vulnerable and real-fix-patched UDR image, under no credentials and a valid, correctly-scoped bearer token minted with the NRF's own private key for a real, registered network-function identity (not a full client-credentials round-trip, out of scope here). With no credentials, both builds correctly returned HTTP~401 before the underlying CWE-285 bug could matter. With a valid token, the vulnerable build's leaks reproduced exactly as in every OAuth2-disabled result, and the real fix closed both while preserving the legitimate path. OAuth2 enforcement and the code-level fix are therefore independent, complementary layers: OAuth2 narrows the threat model to credentialed callers but provides no additional protection against this bug once that bar is cleared, so the real fix remains necessary regardless. Full method and raw evidence: \texttt{docs/FREE5GC\_OAUTH2\_ENFORCEMENT\_RESULTS.md} and \texttt{reports/reachability/free5gc\_oauth2\_enforcement.json}.

A separate repeatability check, using unique prompt markers per call, targeted the Claude CLI and AIxTech gateway results: all 12 AIxTech calls completed; nine of twelve Claude CLI calls completed, with three Opus calls retained as access failures. A controlled OpenAI repeatability attempt recorded the requested temperature and seed for all twelve runs, but the locally supplied API key was rejected with HTTP 401 before generation — environment-limited evidence, not a model-quality failure.

\section{Discussion}

\subsection{Interpreting the Confirmation-Rate Progression}
\label{sec:confirmation-rate-progression}

The rise from 1/6 in round 1 to 5/6 in round 5 is not evidence of a steadily improving model or pipeline. Round 3's drop to 1/6, despite a genuine bug fix introduced that round, shows a working retry mechanism is not the same as one that reliably finds the correct fix. Round 4's jump traces more readily to the two implementation-defect fixes than to any change in model capability, given the same model and largely the same prompt were used across rounds 3 and 4, and the improvement coincides precisely with the fence-crash signature disappearing from every report — a correlational reading, not a causal proof. The records do support a more general caution, one the patch-validation false-acceptance finding (Section~\ref{sec:patch-generation-validation}) makes sharper: a harness defect of this kind can distort a reported result in either direction, so neither a low nor a high raw count in this project's own catalogue should be read as a reliable floor or ceiling without independent trace verification.

The SQL Injection class's behaviour across rounds (confirmed in round 1, unconfirmed in rounds 2--4, confirmed again in round 5) is consistent with the project's own stated caveat that a single-shot, non-averaged protocol can flip for the same CVE between runs, since neither the model's sampling nor the surrounding pipeline state is guaranteed identical run-to-run even with a fixed seed. This is a property of the evaluation protocol, not evidence that any one class is inherently harder than another.

\subsection{Why Patch Validation Lagged Confirmation}
\label{sec:patch-validation-lag}

The central finding on patch acceptance is not a rate but the design flaw established in Section~\ref{sec:patch-generation-validation}: the two-check criterion cannot distinguish a deliberate fix from an unrelated crash bug, as round 5's confirmed false acceptance for CVE-2026-78683 shows directly. This reframes every raw patch-acceptance count in this chapter: a nonzero count means ``the automated criterion was satisfied,'' not ``a correct fix was produced,'' until each case is traced by hand as round 4 and round 5 were here. This is not an idiosyncrasy of this project's own harness: PVBench's independent, 209-case benchmark found over 40\% of patches three state-of-the-art automated-repair systems had validated as correct failed its stronger, developer-authored test standard \cite{pvbench}, and VulnRepairEval similarly found that, under exploit-based differential validation, the best-performing of twelve evaluated models repaired only 5 of 23 Python CVEs \cite{vulnrepaireval} in that baseline evaluation: a low result under that criterion, not a measured before-and-after reduction caused by switching validation standards, since the study does not report re-scoring the same patches under a weaker oracle first. Round 5's single false acceptance is therefore a small-sample instance of a pattern now independently measured at benchmark scale, not a defect unique to this project's own criterion.

Two distinct 48-run datasets are reported in this chapter (Section~\ref{sec:multi-model-comparison}; Section~\ref{sec:corrected-validator}'s four-bug retest) and should not be collapsed into one figure. Given the false-acceptance finding above, even the corrected 3/48 figure should be read cautiously, since the acceptance criterion can still accept a patch whose vulnerable route simply crashes; no overall reliability gain is claimed beyond the specific behavioural changes already listed. Across these two datasets and, separately, round 5's own six-record run: zero patches, across all three, have both passed the original two-check criterion \emph{and} been confirmed correct by trace-level inspection. This is narrower than a claim about every patch in this project: it does not describe the three real-upstream maintainer fixes or the 6 content-verified artifacts reported elsewhere, all of which passed a stronger standard, short of independently confirmed general correctness.

The corrected validator (Section~\ref{sec:corrected-validator}) directly addresses the specific failure mode this subsection describes, but only partially: it distinguishes a deliberate rejection from a crash on the exploit side, but does not close the equivalent gap on the benign side. This is a genuine improvement to exploit-side discrimination — it found zero \texttt{confirmed\_fix} results on a full sixth catalogue round, and only 4--5 of 6 per model on the later 36-run hosted comparison — but its benign-side check remains a screen for gross regressions, not a correctness proof.

A separate, more procedural finding reinforces the same caution: three of the four harness defects found during the patch-validation investigation were pure implementation bugs, not model failures, and plausibly suppressed some earlier counts, though this project did not re-run those earlier attempts to measure how many. This is consistent with the pattern already observed for exploit confirmation (Section~\ref{sec:confirmation-rate-progression}): a nontrivial share of this project's apparent capability gaps has turned out to be harness defects rather than fundamental model limitations, cutting in both directions — a harness defect can suppress a real success (round 3's markdown-fence crashes) or manufacture a false one (round 5's \texttt{NameError}).

\subsection{Runtime and Model-Size Findings}

Confirmation rate did not track parameter count (Table~\ref{tab:multi-model}): the 7B qwen2.5-coder model outperformed both the 9B (gemma2, 0/6) and 13B (codellama, 2/6) models. This project's comparison (a single deterministic shot per CVE per model, with differing architectures and qwen2.5-coder:7b carrying prior prompt-tuning exposure the others did not) is not designed to isolate a cause and should not be read as a general-purpose ranking. The codellama:13b and gemma2:9b runtime anomalies (respectively far slower than a larger model, and one 15--25x single-run outlier) were not root-caused in this project; they are reported as observed rather than explained by an unverified guess.

\subsection{Classification Reliability and the Structured-Data Advantage}

Preferring an advisory's own structured CWE field over free-text keyword matching removed every classification error observed in this catalogue (Table~\ref{tab:ablation}), supporting this precedence rule as a deliberate design choice. The one full miss under prose-only matching (CVE-2026-42208) suggests keyword-based classification is fragile when an advisory describes a mechanism without the vulnerability class's own common vocabulary — a gap a structured field sidesteps entirely. The single exact-CWE mismatch points to a narrower limitation: a fixed family-to-representative-CWE mapping cannot reproduce an analyst's more specific subtype judgment (here, CWE-80 assigned instead of the mapping's default CWE-79 for any cross-site-scripting pattern), a property of how the mapping was hand-encoded, not of prose matching as a technique — it does not establish that prose-based classification is unreliable in general, only that a coarse family mapping loses subtype precision a structured field preserves.

\subsection{Relationship to the AIxCC/OSS-CRS Benchmark Context}
\label{sec:aixcc-comparison}

The 86\% discovery / 68\% patch figures introduced in Chapter~1 are DARPA's own aggregate across all seven AIxCC finalist systems, not a per-system figure and not specifically ATLANTIS's own result. Direct numerical comparison between that aggregate and this project's own rates would also compare results obtained under materially different tasks, software, and evaluation conditions: AIxCC's finalists discovered previously \emph{unknown} bugs seeded into large, real competition codebases under a shared, adjudicated benchmark, while this project confirms and reproduces \emph{already-published} bugs against six small, generated stand-in targets. The two results are not on the same scale or denominator, and no numerical comparison between them is drawn here.

The comparison that holds is qualitative, not numerical: both AIxCC-class systems and this project treat an unverified claim as insufficient on its own and require executable evidence before a discovery or a patch is trusted. FuzzingBrain, a real AIxCC finalist, uses a comparable staged reachability-then-triage architecture and reports that its call-graph analysis narrows a codebase from thousands of functions to a more tractable reachable subset \cite{fuzzingbrain}, qualitatively consistent with this project's own reachability-filtering result; however, its published paper does not report a specific percentage reduction figure comparable to this project's 96.1\%, so no quantitative comparison is drawn here, only the shared qualitative design choice.

\subsection{Limitations, Trade-offs, and Sources of Uncertainty}

The exploit-artifact generation results above were obtained against a generated Flask stand-in reproducing each advisory's described bug pattern, not the actual named upstream package; a confirmed exploit therefore demonstrates that the described pattern is exploitable as reproduced, not that the real package is exploitable when actually installed and run.

This limitation is now partially, not fully, closed: Section~\ref{sec:real-upstream-validation} demonstrates the same evidence-gating discipline against a real, pinned-version PyPI package (CVE-2026-23949), reaching this project's strongest evidence tier among the Python-based cases, but this remains one case chosen for tractability out of six, not a claim the remaining five could be validated the same way without comparable effort.

The reachability result avoids the reproduction-vs-real-package limitation by a different route, since it operates on the real, cloned upstream free5GC source, and its original compile-only bound (\texttt{go build} succeeding proves syntactic validity, not runtime correctness) has since been closed for all four handlers: runtime confirmation (Section~\ref{sec:free5gc-runtime-harness}), over real HTTP against both the vulnerable and fixed commits, confirms the fix closes all four handlers' exploitable behaviour while preserving legitimate function for the operations tested — one of three real-upstream, runtime-confirmed cases alongside \texttt{jaraco.context} and OpenEMR (Section~\ref{sec:openemr-validation}), and the only one where all four manually selected handlers reached this standard.

Deploying and testing the full free5GC core network stack (AMF, SMF, and the rest) remains out of scope. OAuth2 enforcement, which the fuller deployment's real NRF enables by default, was explicitly disabled in the runtime results described earlier in this chapter to reach the handlers under test; a later follow-up, also reported in this chapter (Section~\ref{sec:final-evidence-freeze}), re-ran a subset of these same checks with OAuth2 enforcement turned on and found it does not change this CVE's exploitability by a credentialed caller, so this out-of-scope statement applies specifically to the OAuth2-disabled results described earlier, not to this project's evaluation as a whole.

The multi-model comparison's single-shot, non-repeated design (one run per CVE per model, even with sampling pinned) means individual model rankings in Table~\ref{tab:multi-model} should be read as one data point rather than a statistically powered result: an explicit, acknowledged trade-off made to keep the eight-model, 48-run comparison tractable within the project's timeframe rather than to claim more statistical confidence than the design supports.

\section{Summary and Implications}

An evidence-gated, dynamically-confirmed pipeline of this kind can produce useful confirmation evidence on a small, fixed catalogue of already-disclosed vulnerabilities. Patch generation and validation are substantially harder to achieve reliably than exploit confirmation, and harder still to trust once a validation criterion is checked by trace-level inspection rather than taken at its own flag. No numerical comparison to AIxCC finalist systems is drawn here (Section~\ref{sec:aixcc-comparison}); the two bodies of work share only a qualitative commitment to executable evidence over unverified claims. Rather than treating exploit confirmation and patch generation as symmetric problems solvable by the same prompt-and-model combination, these results point toward separate, class-specific tuning or a larger model tier before patch generation can be trusted as a validated output. For practitioners considering a similar system, the reachability-filtering result offers a more immediately transferable takeaway: narrowing an LLM's analysis scope via real, AST-based call-graph reachability produced a large, real scope reduction (96.1\%) and an initial patch verified to compile against the genuine upstream dependency graph for all four manually selected handlers, without at that stage requiring dynamic confirmation. Reachability filtering and dynamic confirmation are not mutually exclusive: a minimal, dependency-scoped harness (Section~\ref{sec:free5gc-runtime-harness}) first added runtime evidence for one filtered-in handler (DELETE) without deploying the full upstream stack, and a fuller Docker-based deployment subsequently extended the same dynamic standard to all four handlers, without ever needing the rest of the free5GC core network stack.

\chapter{Conclusion}

\section{Summary of the Project}

This project set out to extend an existing exploit-confirmation prototype so that suspected vulnerabilities could be confirmed and candidate fixes evaluated with genuine evidence, rather than accepted on the strength of a plausible-sounding generated artifact alone. Two complementary capabilities were built and evaluated toward this goal. The main pipeline advanced a CVE from advisory intake through classification, exploit-artifact generation, dynamic execution, self-improvement, and patch generation and validation, evaluated across five rounds against a six-CVE catalogue and, separately, across eight locally hosted models. A second, independent capability ported and extended an earlier reachability-filtering prototype to operate on real, disclosed free5GC source, narrowing a real 102-function file to 4 relevant functions and verifying a generated patch against the genuine upstream project; the DELETE handler (CVE-2026-40246) was first runtime-confirmed using a minimal MongoDB-only harness, and a fuller deployment with a real free5GC NRF subsequently extended runtime confirmation to all four selected handlers (CVE-2026-40245 through CVE-2026-40248), rather than compiled but never executed, making free5GC the project's most complete demonstration of the full exploit-confirmation-and-patch-validation methodology against a real, disclosed, compiled upstream vulnerability.

\section{Key Findings}

Eight findings stand out from the results reported in Chapter~4; full detail and evidence for each is in the cross-referenced section, not repeated here.

\begin{enumerate}
\item Dynamic exploit confirmation reached 5/6 CVEs in the best local round, and every catalogue class confirmed at least once overall (Section~\ref{sec:limitations-method-related}).

\item Two confirmation-rate swings across rounds traced to fixable implementation defects, not model capability: a reported ``confirmation rate'' is only as trustworthy as its own harness.

\item Patch acceptance lagged confirmation throughout: at most 1/6 per local round, 0/48 then 3/48 across the two 48-run comparisons.

\item The critical finding: the validation criterion behind that ``passing'' flag was itself found, by trace-level inspection, to accept a patch for the wrong reason at least once, since it cannot distinguish a deliberate block from an unrelated crash. Every raw pass/fail count in this project should accordingly be read as what the harness reported, not an automatically trustworthy verdict (Section~\ref{sec:patch-generation-validation}).

\item Correcting that criterion into a four-outcome verdict and scaling up (a sixth local round, a 36-run hosted comparison) did not increase heuristic screening passes beyond 4--5/6 per model, under a criterion itself limited to crash-absence; not all remaining failures represent incorrect patches, given the known XSS oracle issue (Section~\ref{sec:corrected-validator}), and reported cost tracked model tier, not pass rate.

\item A real, pinned-version PyPI package (\texttt{jaraco.context}) reached this project's full evidence-gating standard against the actual named package, not a reproduction: one case of six (Section~\ref{sec:real-upstream-validation}).

\item The same standard transferred to a second, unrelated domain: OpenEMR's GHSA-q366-cv5v-83w8, confirmed against the real, unmodified application (Section~\ref{sec:openemr-validation}).

\item A third real-upstream case, free5GC, closed a shared one-line defect enabling unauthorized read, collection-wide read, write, and delete across all four manually selected handlers (the malicious side relying on a heuristic leaked-data signal rather than exact-content matching, Section~\ref{sec:free5gc-runtime-harness}), while the legitimate path was separately verified for two of the four (single-record read and delete) — this project's most complete end-to-end case.
\end{enumerate}

\section{Contributions}

This project's contributions are as follows. (1) A dynamic-execution and self-improvement extension to an existing exploit-confirmation pipeline, evaluated with real subprocess and HTTP evidence rather than static description. (2) A two-check, evidence-gated patch-acceptance mechanism and a corrected four-outcome verdict (Section~\ref{sec:corrected-validator}), built specifically in response to a confirmed false acceptance the original criterion could not detect, and itself subsequently audited for what its own benign-route check does and does not establish. (3) A reachability-filtering capability applied in this project to real, disclosed free5GC source, verified by compile and then by runtime confirmation for all four manually selected handlers (CVE-2026-40245 through CVE-2026-40248), finding the underlying bug to be a full CRUD bypass rather than a single-record issue — this project's most complete real-system case. (4) A reproducible, sampling-pinned eight-model comparison and a second, 36-run comparison across six hosted Claude models, under an identical protocol with real token accounting and a reported cost estimate. (5) Two further real-upstream validation cases against actual, unmodified software: a pinned-version PyPI package (Section~\ref{sec:real-upstream-validation}) and a disclosed OpenEMR advisory in a second, unrelated application domain (Section~\ref{sec:openemr-validation}).

\section{Limitations}

The results in this project should be read within stated bounds. The main pipeline's exploited targets are generated reproductions, not the real named packages, for all six main-catalogue CVEs; a confirmed exploit demonstrates the described pattern is exploitable as reproduced, not that the real package is. One of the six, CVE-2026-23949, additionally has a separate, dedicated experiment against the real, pinned-version package (Section~\ref{sec:real-upstream-validation}) — a single case selected for tractability, not evidence the remaining five could be validated the same way without comparable effort.

The free5GC reachability result avoids this limitation by a different route, operating on real, cloned source: all four manually selected handlers' patches were verified to compile, and all four (CVE-2026-40245 through CVE-2026-40248) were additionally confirmed at runtime, without deploying the rest of the core network stack or enabling OAuth2 enforcement; a follow-up with OAuth2 enforcement enabled is reported in Section~\ref{sec:final-evidence-freeze}.

The eight-model local comparison used a single deterministic shot per CVE per model, and its strongest-confirming model carried prior prompt-tuning exposure the others did not, a real confound; the 36-run hosted comparison shares this single-shot design and adds its own, since the Claude CLI exposes no temperature or seed control at all. Patch generation and validation remained the main unresolved engineering challenge: the hosted comparison recorded 4--5 of 6 heuristic screening passes per model, and known XSS oracle errors prevent interpreting all remaining failures as incorrect patches; whether per-class prompt tuning would close it further was not tested.

The extended-access comparison, the OAuth2-enforced follow-up, and the prompt/cache repeatability check (Sections~\ref{sec:extended-access-comparison} and~\ref{sec:final-evidence-freeze}) are reported in Chapter~4 alongside the results they extend, not repeated here: in summary, OAuth2 enforcement and the code-level fix are independent, complementary layers, and every repeatability attempt's limits were environment-specific, not evidence of model-quality failure.

\Needspace{8\baselineskip}
\section{Future Work}
\label{sec:future-work}

Five directions follow directly from the limitations above.

\begin{enumerate}
\item The cross-model \texttt{not\_blocked} result for Cross-Site Scripting (Section~\ref{sec:claude-multi-model-comparison}) is a heuristic screening result, not confirmed patch incorrectness: at least one recorded failure was a false-positive marker signal in the generated target rather than a genuine patch defect (Section~\ref{sec:corrected-validator}). Repairing the XSS oracle first — so that it checks actual rendered HTML output rather than only for marker absence — is a prerequisite before any per-class tuning pass on XSS patching can be meaningfully interpreted.

\item Patch generation would benefit from the same bounded, per-class tuning process already applied successfully to exploit-artifact generation in this project, starting with Cross-Site Scripting once the oracle repair above is in place. Any such tuning should be evaluated on held-out CVEs not seen during prompt development, since repeatedly tuning and scoring on the same six cases demonstrates engineering fit to those cases, not generalisation to unseen tasks.

\item The free5GC reachability work's runtime validation (Section~\ref{sec:free5gc-runtime-harness}), now confirmed for all four of its handlers (CVE-2026-40245 through CVE-2026-40248) under a fuller deployment with a real NRF, has since been extended with OAuth2 enforcement turned on (Section~\ref{sec:final-evidence-freeze}): the question of whether OAuth2 changes these CVEs' exploitability is answered in the negative for the two malicious read checks and one benign read under the tested bearer-token conditions, but that follow-up only ported 3 of the original 5 runtime checks and minted its bearer token directly with the NRF's own private key rather than through a live client-credentials HTTP round-trip against NRF's own \texttt{/oauth2/token} endpoint. Porting the remaining unauthorized-write and confirmed-delete checks to the OAuth2-enabled harness, implementing the full client-credentials flow rather than a directly-minted token, and standing up additional network functions (AMF, SMF, and the rest) to test behaviour beyond UDR's own component boundary all remain future work, unifying the reachability engine's real-source analysis with the main pipeline's dynamic-confirmation discipline at greater scope.

\item The main pipeline's exploited targets could be moved from generated reproductions toward the actual named upstream packages for a larger subset of the catalogue than the one case demonstrated here, extending Section~\ref{sec:real-upstream-validation}'s methodology to the remaining five classes.

\item The hosted-model comparison could be extended with sampling controls once the Claude CLI (or an equivalent hosted interface) exposes them, and repeated across multiple shots per CVE per model to move from one data point per model toward a statistically powered ranking.
\end{enumerate}

\section{Validation Criteria (Quick Reference)}

Full definitions, caveats, and audited scope for every term below are given once, in Section~\ref{sec:evaluation-metrics} and Section~\ref{sec:corrected-validator}; this list restates only the term and its one-line gist for lookup convenience.

\begin{itemize}
\item \textbf{Dynamically confirmed}: a recorded subprocess execution outcome, HTTP exchange, or compiled-harness run, each real and not merely described.
\item \textbf{Patch accepted by the two-check criterion} (raw \texttt{patch\_validated} field): exploit fails and \texttt{/health} still returns 200; cannot distinguish a deliberate fix from an unrelated crash (Section~\ref{sec:patch-generation-validation}); superseded by \texttt{patch\_verdict} below.
\item \textbf{\texttt{patch\_verdict}} (Section~\ref{sec:corrected-validator}): \texttt{confirmed\_fix} (the historical label used by every report this thesis cites; renamed \texttt{heuristic\_fix\_screened} in newly generated reports), \texttt{regression\_broke\_route}, \texttt{inconclusive\_crash}, or \texttt{not\_blocked}, distinguishing a crash on the exploit side from one on the benign side.
\item \textbf{Correct patch / stronger bounded validation}: the strict sense (independent second-reader adjudication) is not measured anywhere in this project; a stronger bounded-validation sense was established for three real-upstream cases and six LLM-generated artifacts available at reassessment time (Section~\ref{sec:corrected-validator} states the exact, non-uniform malicious- and legitimate-side checks used for each), short of general correctness.
\item \textbf{Compile-verified} (free5GC, original evidence tier): \texttt{go build} succeeds against the real, live-cloned upstream module; weaker than dynamic confirmation, since superseded by runtime confirmation.
\item \textbf{Runtime-confirmed} (free5GC, all four handlers): the real, cloned module built, run, and exercised over real HTTP for both commits (Section~\ref{sec:free5gc-runtime-harness}); meets the \textbf{Dynamically confirmed} standard above.
\end{itemize}

\section{Relationship to AIxCC/OSS-CRS Vocabulary (Condensed)}
\label{app:crs-mapping}

This project's stages line up with AIxCC/OSS-CRS vocabulary as follows, condensed from this project's own internal mapping document. Stage 1 (advisory fetch) corresponds to OSS-CRS's \texttt{prepare} phase, except that it pulls an already-known advisory rather than preparing to discover one. Stage 3.5 (exploit-artifact generation) corresponds to \texttt{build-target}, except that it generates a minimal reproduction rather than compiling the real upstream project (the single biggest structural gap versus a real CRS, per Section~\ref{sec:limitations-method-related}). Stages 2, 3, 3.6, and 3.7 together correspond to the \texttt{run} phase's triage-and-verify loop. The two capabilities are best framed as complementary but partial: (1) the confirm-and-patch back half of a real CRS's loop, evaluated one known CVE at a time, and (2) a real, AST-based scope-reduction front half (\texttt{src/reachability/}) proven against one real, disclosed free5GC vulnerability. Neither claims the hardest capability a full CRS needs (discovering an \emph{unknown} bug in an unmodified codebase) which this project does not attempt.

\section{free5GC LLM-Generated Patch: Multi-Model Comparison}
\label{sec:free5gc-llm-patch-sweep}

The free5GC result reported above uses the real upstream maintainers' own fix commit, checked out directly, not a model-generated artifact. A separate, later experiment instead asked a real LLM to \emph{write} the fix itself, for the one handler, \texttt{HandleApplicationDataInfluenceDataSubsToNotifyGet}, that the reachability engine's deterministic rule-based patcher is already documented to under-fix: that patcher inserts only one of the two \texttt{return} statements the handler's two separate early-exit validation blocks each need, since both share the identical missing-\texttt{return} bug pattern. The handler tests whether the generated patch repairs both known early-exit sites, including the site missed by the current deterministic patcher.

A local model (\texttt{qwen2.5-coder:7b}, via Ollama, zero recorded API charge; electricity and hardware use were not separately measured) correctly inserted \texttt{return} after both occurrences, a strict improvement over the rule-based patch. Two further robustness issues were found and fixed directly as a consequence of this comparison, both in the shared patch-generation code path used by every model and provider in this project, not specific to any one model. First, the patch-generation prompt template was originally written for a C target and retained its C-specific framing and code-fence language even when applied to free5GC's Go source; a language-aware system prompt and fence selection, keyed on the target file's extension, was added. Second, one hosted model twice ignored an explicit "no commentary" instruction in two different ways across two separate attempts (once appending an explanation after a closing code fence, once with no fence at all). In both cases the underlying fix was logically correct, but trailing prose corrupted the surrounding Go source and caused a compile failure unrelated to the fix itself. This was resolved by truncating the model's response at the target function's own final, unindented closing brace unconditionally, rather than relying on fence detection, since every target in this comparison is syntactically a single complete function.

This comparison does not control for training-data memorisation: the real, public fix commit may appear in some models' training data, and a model reproducing it from memory is, in this experimental design, indistinguishable from one genuinely re-deriving it from the function body and vulnerability description alone. Each model was also run once; \texttt{qwen2.5-coder:7b} was observed to produce a textually different but semantically identical patch on a repeat run, a direct, if harmless, demonstration that single-run results in this comparison do not capture run-to-run variance.

\section{free5GC Adversarial Bypass-Probe: Can a Model Find a Way Past the Real Fix?}
\label{sec:free5gc-bypass-probe}

The comparison above asks whether a model can \emph{write} the fix. A separate, later experiment asks the opposite question: given the real, already-deployed upstream fix, can a model find an HTTP-request-level trick (encoding, case, path manipulation, headers, trailing or duplicate path segments) that still reaches the protected resource? The upstream fix closes the known missing-return fall-through paths. This bounded probe asks whether the selected models can propose a request-level way around that fix. Each of the eight locally-hosted models and eleven named hosted Claude models was asked to propose one concrete HTTP request. The historical prompt described the patched handlers as having no remaining code-path gap. This was a framing assumption supplied to the models, not an exhaustive property established by the experiment. The result is interpreted here only as a bounded request-level probe of the known fix. Each successfully parsed, valid proposal was then \emph{actually executed} against the real, already-built upstream-fix image (\texttt{free5gc-udr-custom:patched}) running on the same real MongoDB and free5GC NRF deployment used throughout this chapter, not evaluated by inspection.

\textbf{Result: zero genuine bypasses were found}, across every model tested, local or hosted.

A real defect in this experiment's own classifier was found and fixed before any result was reported. The first version flagged three models as having found a successful bypass purely because their proposed request returned a 200 response containing the protected data, without checking whether that request actually differed from the ordinary, fully authorised request. Two of the three proposals were, after inspection, byte-for-byte identical to the correct, legitimate path; a third used URL encoding (\texttt{\%2F}) that decodes back to the identical canonical path. None of these are bypasses of anything (they are the intended request, which obviously returns 200), and two of the implicated models' own stated reasoning (a claimed trailing-dot trick, a claimed case variation) did not even match the request they actually issued, itself a finding about model reliability on this task rather than about the target. The classifier was corrected to require that a proposal's URL-decoded form differ from the canonical, fully authorised path before it can count as a genuine attempt at all; every result below reflects that corrected check, re-derived from the already-captured request and response data with no model re-queried.

representative pair verbatim (the reachability track's patch-
generation system and user prompts (\texttt{src/reachability/patch.py})) so a reader can see this project's actual prompting style without
opening the repository.

\begin{verbatim}
SYSTEM PROMPT (Go target; a near-identical C/kernel variant is
selected when the target file is not Go):

You are a Go backend developer writing a minimal security fix for an
HTTP handler. Output ONLY the complete corrected function body (same
signature, same style), no markdown fences, no commentary. Keep the
change as small as possible - do not refactor or rename anything not
required by the fix.
\end{verbatim}

\begin{verbatim}
USER PROMPT TEMPLATE:

CWE: {cwe}
Vulnerability: {explanation}

Fix this function. Preserve its exact signature and behavior for
valid inputs; only add the missing bounds/validation/sanitization
needed to close the reported issue.

```{lang}
{body}
```
\end{verbatim}

When a prior exploit attempt crashed the target, one further
paragraph is appended to the user prompt, grounding the fix in that
confirmed failure rather than only the triage stage's prose
description:

\begin{verbatim}
A generated proof-of-vulnerability harness confirmed this exact bug
crashes the original code:
```
{last 1000 characters of the crash log}
```
The fix must make this exact harness survive without crashing.
\end{verbatim}
